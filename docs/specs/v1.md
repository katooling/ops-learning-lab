# Version one product specification

## Problem Statement

Useful operational knowledge is often scattered across conversations, notes,
documents, screenshots, code references, and tool output. Reconstructing that
context later is slow, and reading a summary does not prove that a learner can
apply the knowledge or choose evidence with the correct scope.

The Learner needs a private, local way to capture raw work context without
publishing it, turn selected material into reviewed Learning Packs, practice
with safe deterministic Scenarios, demonstrate mastery, and revisit the lesson
later. The product must preserve provenance and must never silently treat raw
or generated claims as verified truth.

## Solution

Build a local-first Learning Lab with a deterministic Python core, a small
command-line interface, and a purpose-built browser Product Shell.

Capture Mode stores an Intake Bundle in a Private Intake Store, proposes a Pack
Match, and stages a Pack Update without interrupting ongoing work. The Learner
reviews and promotes sanitized material into an accepted Learning Pack.

Learn Mode guides the Learner through one consistent Learning Loop:
`Map -> Predict -> Try -> Prove -> Explain -> Review`. Safe local Scenarios
produce structured observations. The Product Shell evaluates Evidence Cards
against Claims and advances Mastery State only when a Learner Attempt
demonstrates the required ability. A later successful review proves retention.

Version one proves this journey with one synthetic Codex ETL Learning Pack and
a sanitized standalone export.

## User Stories

1. As a Learner, I want to capture pasted work context, so that useful learning is not lost in a long conversation.
2. As a Learner, I want to capture a local file, so that notes and sanitized research can enter the same learning workflow.
3. As a Learner, I want each captured item to retain provenance, so that I know where a later claim came from.
4. As a Learner, I want repeated capture of the same bytes to be idempotent, so that retries do not create misleading duplicate sources.
5. As a Learner, I want raw Intake Bundles stored privately, so that capture does not publish sensitive context.
6. As a Learner, I want Intake Adapters to be read-only, so that learning cannot alter source conversations or systems.
7. As a Learner doing other work, I want Capture Mode to finish with a concise summary, so that I can return to the active task.
8. As a Learner, I want Capture Mode to avoid starting a lesson, so that saving context does not cause an unexpected interruption.
9. As a Learner, I want the system to propose a related Learning Pack with reasons, so that I can judge whether the match is correct.
10. As a Learner, I want ambiguous Pack Matches to require my choice, so that unrelated knowledge is not silently merged.
11. As a Learner, I want the system to propose a new pack when no strong match exists, so that novel topics remain distinct.
12. As a Learner, I want generated changes staged before application, so that accepted content remains stable during capture.
13. As a Learner, I want a Pack Update to show additions, changes, and removals, so that review is understandable.
14. As a Learner, I want each proposed Claim linked to its sources, so that I can inspect its support.
15. As a Learner, I want Operational Facts marked current, historical, contradicted, or unverified, so that old evidence is not presented as current truth.
16. As a Learner, I want contradictions highlighted, so that I can resolve them instead of silently replacing history.
17. As a Learner, I want Promotion to sanitize selected material, so that accepted packs contain only what the lesson needs.
18. As a Learner, I want private details excluded by default, so that omission rather than disclosure is the safe failure mode.
19. As a Learner, I want the Product Shell to distinguish raw intake, staged updates, accepted packs, and exports, so that I understand each trust boundary.
20. As a Learner, I want to browse accepted Learning Packs locally, so that learning works without a hosted account.
21. As a Learner, I want every lesson to begin with a system Map, so that I understand components and boundaries before acting.
22. As a Learner, I want to record a prediction before seeing the result, so that the lesson tests my model rather than hindsight.
23. As a Learner, I want to manipulate a resettable Scenario, so that I can explore consequences without operational risk.
24. As a Learner, I want Scenario results to be deterministic, so that the same seed and actions reproduce the same evidence.
25. As a Learner, I want to select Evidence Cards for a Claim, so that I practice matching proof to scope.
26. As a Learner, I want feedback when evidence proves only a neighboring claim, so that I learn to avoid overclaiming.
27. As a Learner, I want to explain the result in my own words, so that progress requires reasoning rather than clicking.
28. As a Learner, I want confidence recorded before and after a Scenario, so that I can recognize calibrated and uncalibrated judgment.
29. As a Learner, I want hints recorded in the Learner Attempt, so that completion evidence distinguishes independent and assisted performance.
30. As a Learner, I want reading a lesson to count only as Introduced, so that exposure is not mistaken for demonstrated skill.
31. As a Learner, I want successful application to advance mastery to Demonstrated, so that progress reflects earned ability.
32. As a Learner, I want a later review before mastery becomes Retained, so that the product measures learning over time.
33. As a Learner, I want interrupted attempts restored after reload, so that a browser interruption does not erase work or invent completion.
34. As a Learner, I want to reset a Scenario without changing canonical progress, so that experimentation remains safe and repeatable.
35. As a keyboard user, I want to complete the full Learning Loop without a pointer, so that the core experience is accessible.
36. As a Learner on a narrow screen, I want the Learning Loop to remain usable and ordered, so that layout does not hide required steps.
37. As a Learner, I want Activity Renderers isolated from private intake and mastery state, so that a bounded activity cannot bypass product rules.
38. As a Learner, I want Scenario results to include a state hash, so that an attempt can prove which deterministic state produced its evidence.
39. As a Learner, I want to export an accepted pack as a standalone artifact, so that reviewed learning can be shared later.
40. As a Learner, I want export to use an allowlist, so that unreviewed source material cannot enter accidentally.
41. As a Learner, I want export to fail when a private canary is detected, so that privacy has executable proof.
42. As a Maintainer, I want all repository fixtures to be synthetic, so that tests and examples remain safe to publish.
43. As a Maintainer, I want one verification command, so that contributors can prove tests, compilation, installation, and publication safety consistently.
44. As a Maintainer, I want one black-box journey through capture, learning, restart, review, and export, so that release evidence covers the complete product boundary.
45. As a Maintainer, I want packs to declare Renderer Capabilities instead of technologies, so that learning meaning survives interface changes.
46. As a Maintainer, I want generated or agent-proposed artifacts validated deterministically, so that agent judgment cannot bypass canonical contracts.
47. As a Maintainer, I want every mastery change linked to the Learner Attempt that earned it, so that progress is auditable.
48. As a Maintainer, I want older contradicted facts preserved as history, so that updates do not destroy useful provenance.

## Implementation Decisions

- Version one is a personal, local product with no account or hosted service.
- The runtime uses standard-library Python and a browser. It has no third-party
  runtime dependencies.
- The deterministic core owns identifiers, hashes, schemas, provenance,
  matching rules, contradiction status, promotion gates, Scenario evaluation,
  Learner Attempts, Mastery State, review scheduling, and export allowlists.
- Agent judgment may extract candidate material, draft explanations, and
  propose matches. Deterministic validation governs every persisted or exported
  artifact.
- Raw source bytes live only in the Private Intake Store. The public repository,
  Product Shell, Activity Renderer, and exporter cannot read that store except
  through narrowly defined capture and Promotion boundaries.
- Capture is content-addressed and idempotent.
- Capture Mode stores intake and stages a Pack Update. It does not change
  accepted pack content or start a lesson.
- Pack matching is propose-first. Ambiguous matching always requires Learner
  selection.
- Promotion is the only path from private intake to accepted Learning Pack
  content.
- Operational Facts include provenance, observation time, and status.
- The Product Shell owns canonical navigation, attempt state, evidence
  evaluation, mastery, review, persistence, recovery, accessibility framing,
  and export.
- The built-in Activity Renderer receives immutable sanitized inputs and emits
  structured results. It cannot read private intake, award mastery, evaluate
  evidence, or write canonical state.
- Learning Packs declare versioned Renderer Capabilities and outcomes rather
  than interface technologies.
- Canonical reviewed content and local state use explicit, versioned Markdown
  and JSON contracts.
- File updates that affect canonical state are atomic.
- Version one contains one synthetic Codex ETL Learning Pack. The Scenario
  traces a record through source, raw storage, normalization, validation, and a
  downstream representation.
- Publishable Artifacts contain only promoted pack content and sanitized
  snapshots.

## Testing Decisions

- Tests assert externally visible behavior and trust boundaries rather than
  private helper implementation.
- The primary release seam is one black-box browser journey beginning with
  synthetic private input and ending with a sanitized export.
- The journey proves capture, Pack Match proposal, staged review, Promotion, a
  complete Learning Loop, restart recovery, later review, and export.
- Domain tests cover versioned schemas, state transitions, deterministic
  Scenario results, provenance requirements, contradiction handling, and
  evidence sufficiency.
- Filesystem tests cover permissions, symlink escape, atomic updates,
  idempotency, and separation between private and publishable areas.
- Privacy tests place a unique canary in private intake and prove it is absent
  from every repository and exported file.
- Activity boundary tests prove that renderer output cannot mutate canonical
  attempts or Mastery State directly.
- Accessibility evidence includes keyboard-only completion and a narrow
  viewport journey.
- Recovery tests reload midway through each meaningful state transition and
  prove that the attempt resumes without inventing completion.
- Installation and command-line behavior are tested from a clean environment.
- One repository verification command runs unit tests, compilation,
  installation smoke tests, and the publication audit.
- Clearly synthetic fixtures are required. Real or derived-from-real private
  material is prohibited.

## Out of Scope

- Team accounts, shared hosting, administration, or analytics about other
  learners.
- External system mutations, production access, direct messages, or
  credentials.
- Treating generated explanations as verified facts without review.
- A database server or mandatory network service.
- Multiple Activity Renderer implementations.
- Additional Learning Packs before the first vertical slice passes.
- Automatic publication of raw Intake Bundles.
- Full conversation archival as a default adapter behavior.
- A general-purpose course-authoring platform.

## Further Notes

The first release is intentionally narrow. It succeeds by proving that private
context can become reviewed, useful, and retained learning without crossing the
privacy boundary.

Work should be delivered as tracer-bullet GitHub Issues sized for one fresh
implementation context. The release is not complete merely because unit tests
pass; the end-to-end journey, recovery behavior, accessibility checks, and
private-canary export proof must all pass.
